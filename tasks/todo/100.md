# Задача 100. Архитектурная карта ЛР4 и правила событий

- **Лабораторная:** ЛР4
- **Исполнитель:** Илья
- **Сервис:** `platform / all services`
- **Статус:** todo
- **Оценка изменений:** 500–900 строк
- **Зависит от:** нет

## Цель

Зафиксировать целевую событийную архитектуру до внедрения Kafka и определить,
какие текущие Feign-вызовы остаются синхронными, а какие заменяются событиями.

## Что сделать

1. Инвентаризировать все межсервисные вызовы, jobs и создаваемые доменные факты.
2. Оставить HTTP/Feign только для запросов, которым нужен немедленный ответ;
   команды без ответа и рассылку фактов перевести на Kafka.
3. Описать топики, владельцев, producer/consumer, ключ партиционирования,
   retention, число партиций, replication factor, retry и DLT.
4. Утвердить envelope: `eventId`, `eventType`, `eventVersion`, `occurredAt`,
   `producer`, `correlationId`, `actorId`, `payload`.
5. Зафиксировать правила совместимости схем, идемпотентности, PII и удаления файлов.
6. Реализовать machine-readable topology catalog и validator: уникальность топиков,
   владельцев и event types, допустимые зависимости, RF/partition/retention policy.
7. Добавить Gradle verification task и архитектурные тесты, запрещающие новые прямые
   URL, обход принятых портов и несогласованные producer/consumer declarations.

## Критерии готовности

- [ ] Есть актуальная диаграмма и таблица всех взаимодействий.
- [ ] Для каждого Feign-вызова письменно принято sync/async решение.
- [ ] Имена топиков и версии событий единообразны и не дублируются.
- [ ] Topology catalog автоматически валидируется в build и используется далее в CI.
- [ ] Документ содержит план миграции без остановки всей системы.
- [ ] ArchUnit/contract tests проверяют зафиксированные границы.

## API и проверка

Новых HTTP-маршрутов нет. Проверить документацию, архитектурные тесты и
`./gradlew test`; результат является обязательной основой задач 101–112.
