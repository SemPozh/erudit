## Цель

Перенести интеграционные платёжные сценарии без реального шлюза.

## Что сделать

1. Оставить mock mobile receipt verifier и mock webhook provider.
2. Документировать тестовую подпись/receipt в Swagger examples и Config Server.
3. Сохранить idempotency provider event и порядок renewal/cancel/expire.
4. Не добавлять SDK, ключи или сетевые вызовы реального платёжного шлюза.

## Критерии готовности

- [x] Webhook и receipt можно вызвать из Swagger на demo profile.
- [x] Неверная подпись и повтор проверены тестами.
- [x] Ни один тест/Compose контейнер не обращается к реальному провайдеру.

- Реальные email, push и SMS не отправлять; это относится к ЛР4.

- Если фактический diff достигает 1800 строк, остаток вынести в новую задачу до PR.

## Результат проверки (2026-11-04)

- Перенесены local mock mobile receipt и HMAC webhook, реальные провайдеры не используются.
- Receipt привязан к пользователю и provider; повтор не продлевает срок и не
  восстанавливает отменённую подписку. Конкурентное использование проверено.
- Provider event ID и fingerprint хранятся транзакционно. Повтор неизменённого
  события — 204; конфликт содержимого — 409. Старые и равные timestamps не
  меняют новое состояние; события старой подписки не восстанавливают её.
- Flyway V2 добавляет idempotency tables, watermark событий и расширяет
  external_id для provider event ID длиной до 255 символов.
- Demo profile устанавливает фиксированную EXPIRED подписку; Swagger и
  Config Server содержат рабочие receipt/HMAC examples. Mock-ключ поступает
  через переменную окружения Compose, реальные ключи отсутствуют.
- Полная команда `gradlew test openApiValidate build` прошла: 259 тестов,
  0 падений и пропусков. Покрытие payment — 99.1% строк без generated-кода.
- Compose image собран, demo service/DB healthy; `scripts/smoke-payment-events.ps1`
  прошёл через Gateway (подпись примера, неверная подпись, повтор webhook,
  receipt и повтор после отмены). Использовалась отдельная временная БД,
  обычный payment volume сохраняется.
- Документация: `docs/payment-events.md`. Изменения задачи отдельны от №86;
  до слияния №86 целевая база PR — её feature-ветка.
