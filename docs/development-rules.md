# Правила разработки ERUDIT

Правила адаптированы 3 октября 2026 года из учебного репозитория
[`Discipliny/highload_systems`](https://github.com/Discipliny/highload_systems).
Источник задаёт требования поэтапно; ниже они привязаны к текущему состоянию ERUDIT.

## Обязательные правила текущего этапа

### Код и Git

- Использовать стабильные версии Java, Spring Boot и библиотек, соблюдать Java conventions.
- Следовать SOLID, DRY и KISS; разделять контроллеры, DTO, сервисы, доменные модели и репозитории.
- Работать через feature-ветки. Имена коммитов оформлять по Conventional Commits.
- Доменные сущности не использовать как HTTP DTO. Контракт API задаётся в OpenAPI, Java-интерфейсы генерируются из него.

### REST API и данные

- Для основных сущностей предоставлять осмысленный REST CRUD и корректные HTTP-статусы.
- Валидировать входные DTO на границе приложения и бизнес-инварианты в доменном/сервисном слое.
- Ошибки обрабатывать централизованно и возвращать понятное структурированное тело.
- Доступ к реляционной БД выполнять через Spring Data JPA/JDBC. Изменения схемы оформлять Flyway-миграциями.
- Enum хранить в БД строками. Связи и ограничения задавать явно, не полагаться только на проверки Java-кода.
- Любой `findAll` должен иметь пагинацию; максимальный размер страницы — 50.
- В проекте должен быть хотя бы один cursor/infinite-scroll список без общего количества и хотя бы один страничный список с общим количеством в HTTP-заголовке.
- Сложные составные изменения выполнять транзакционно и объяснять необходимость транзакции в коде или описании PR. В проекте должно быть не меньше двух таких сценариев.
- Конфигурацию окружения передавать переменными среды и отражать в Docker Compose.

### Качество и запуск

- Бизнес-логику покрывать unit-тестами, работу с БД и HTTP-сценарии — интеграционными тестами JUnit Jupiter и Testcontainers.
- Целевое общее покрытие кода — не ниже 70%; сгенерированный OpenAPI-код из расчёта исключается.
- Перед слиянием должны проходить тесты, OpenAPI validation и сборка.
- Приложение и его инфраструктура должны собираться и запускаться через Docker Compose.
- Swagger UI и общий OpenAPI 3 контракт должны оставаться актуальными после каждого изменения API.

## Требования следующих этапов

Эти требования учитываются в архитектурных решениях и реализуются отдельными задачами:

1. Декомпозиция на микросервисы: Eureka, Config Server, Spring Gateway, Feign,
   Circuit Breaker; минимум один реактивный сервис с Reactor/R2DBC.
2. Безопасность: Spring Security, JWT в `Authorization`, роли, логика с учётом
   текущего пользователя, хэширование паролей и отсутствие паролей в ответах.
3. Асинхронное взаимодействие: Kafka или RabbitMQ, репликация брокеров,
   несколько топиков и уведомления через брокер.
4. Отдельный файловый сервис после декомпозиции и Clean Architecture во всех сервисах.

Будущие требования не следует внедрять случайно внутри несвязанной задачи. Текущие
интерфейсы и границы доменов должны позволять выполнить их без переписывания API.
