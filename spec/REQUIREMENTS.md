# Требования к проекту ERUDIT

Backend-приложение для развития эрудиции. Первая версия — монолитная (не микросервисы).
Ниже — функциональные требования, сгруппированные по модулям, и нефункциональные требования.

---

## Функциональные требования

### 1. Авторизация и профиль

1) Система должна поддерживать регистрацию пользователя по email и паролю.
2) Система должна поддерживать вход в аккаунт по email и паролю.
3) Система должна выдавать токены доступа и обновления (access/refresh) для авторизации запросов.
4) Система должна поддерживать восстановление пароля по email.
5) Система должна поддерживать подтверждение email при регистрации.
6) Система должна хранить профиль пользователя: имя, аватар, email, дата регистрации.
7) Пользователь должен иметь возможность редактировать имя и аватар.
8) Профиль должен содержать настройки интерфейса и локализации: язык интерфейса, часовой пояс.
9) Профиль должен содержать настройки обучения: любимые тематики (категории), ежедневную цель (минуты/уроки в день).
10) Профиль должен содержать настройки приватности: видимость профиля в поиске и рейтинге, согласие на сбор аналитики.
11) Пользователь должен иметь возможность удалить свой аккаунт.
12) Пользователь должен иметь возможность выйти из аккаунта на всех устройствах.
13) Система должна хранить токен push-уведомлений устройства для доставки нотификаций.
14) Защищёнными (требуют аутентификации) должны быть следующие ресурсы:
    - операции с профилем и настройками;
    - доступ к личному прогрессу, статистике и рейтингу;
    - отправка ответов в квизах и участие в соревнованиях;
    - операции с друзьями (заявки, список, приглашения);
    - оформление и управление подпиской;
    - настройка нотификаций и история уведомлений;
    - отправка событий аналитики от имени пользователя.
15) Публичными (не требующими аутентификации) должны оставаться: регистрация и вход, каталог публичного контента, список категорий и форматов.

### 2. Входное тестирование и оценка AI

1) Система должна проводить входное тестирование уровня эрудиции при первом входе.
2) Входной тест должен содержать вопросы по разным тематикам (наука, история, искусство, география, спорт, технологии, культура).
3) Тест должен оценивать знания по каждой тематике отдельно и в целом.
4) По итогам теста система должна вычислять **числовой рейтинг эрудиции (ER-score)** по единой шкале (например, 0–2000), отражающий общий уровень знаний.
5) На основе ER-score система должна присваивать пользователю **грейд (титул)** из нескольких лиг с подуровнями, например: Новичок → Знаток → Эрудит → Магистр → Легенда. Грейд должен отображаться в профиле.
6) Числовой рейтинг и грейд должны динамически пересчитываться по мере обучения: рост за успехи в квизах, завершение контента, цепочку ежедневных занятий (streak).
7) Результат оценки должен учитываться при подборе образовательной программы.
8) Результат входного теста (числовой рейтинг, оценка по тематикам, грейд) должен храниться в профиле и быть доступен для аналитики.
9) AI-оценка должна интерпретировать ответы и выдавать персональную обратную связь по сильным и слабым сторонам.
10) AI-оценка должна формировать рекомендации по направлениям для развития.

### 3. Подбор образовательной программы

1) Система должна формировать персональную образовательную программу на основе входного теста.
2) Программа должна иметь понятную структуру: набор модулей/тем, каждый модуль — из последовательных уроков; каждый урок состоит из обучающего контента и проверочного квиза.
3) Программа должна отражать понятный прогресс: процент завершения по отдельным модулям, темам и по всей программе.
4) Программа должна учитывать уровень пользователя по каждой тематике.
5) Программа должна учитывать предпочтения пользователя по тематикам и форматам контента. Источники предпочтений: настройки профиля (любимые тематики), выбор при онбординге и входном тесте, поведенческие сигналы из аналитики (с каким контентом пользователь реально взаимодействует чаще).
6) Программа должна содержать последовательность шагов/уроков с понятным прогрессом.
7) Пользователь должен видеть свой прогресс по программе и отдельным тематикам.
8) Система должна предлагать следующий шаг/урок на основе текущего прогресса.
9) Программа должна поддерживать цепочку ежедневных занятий (streak).

### 4. Контент

1) Система должна хранить контент разных форматов: статья, карточка-факт, аудио, видео, комбинированный урок, квиз-блок.
2) Контент должен относиться к тематикам (категориям) и иметь уровень сложности.
3) Контент должен иметь метаданные: теги, время прохождения, автор, статус публикации.
4) Из контента любого формата должны генерироваться карточки-вопросы для квизов.
5) Пользователь должен иметь возможность просматривать каталог контента с фильтрами (категория, формат, сложность, поиск).
6) Пользователь должен иметь возможность просматривать персональную ленту рекомендаций.
7) Система должна помечать премиум-контент и ограничивать к нему доступ (Freemium).
8) Премиум-контент должен открываться только при активной подписке.
9) Потеря подписки не должна удалять прогресс пользователя по контенту.
10) Новый контент должен проходить модерацию перед публикацией.
11) Пользователь должен иметь возможность пожаловаться на контент.
12) Система должна поддерживать мягкое удаление/архивацию контента без потери истории использования.
13) Система должна отслеживать прогресс пользователя по каждому контенту (просмотр, завершение).

### 5. Квизы и соревнования

1) Пользователь должен иметь возможность проходить квизы по изученному контенту.
2) Квиз должен содержать вопросы с вариантами ответа.
3) Квиз должен проверять ответы и сообщать о верности сразу или по итогам.
4) Система должна начислять очки/опыт за верные ответы и завершение квиза.
5) Система должна поддерживать подсказки в вопросах и учитывать их использование.
6) Пользователь должен иметь возможность повторять квизы.
7) Система должна поддерживать ежедневный квиз (одна попытка в день).
8) Система должна поддерживать соревнования между пользователями.
9) Соревнование должно иметь участников, правила и результаты.
10) Пользователь должен иметь возможность приглашать друзей в соревнование.
11) По итогам соревнования должна формироваться таблица результатов участников.
12) Результаты квизов и соревнований должны влиять на рейтинг пользователя.

### 6. Рейтинг и поиск друзей

1) Система должна вести общий рейтинг пользователей по набранным очкам.
2) Система должна вести рейтинг по тематикам и за периоды (день/неделя/месяц).
3) Пользователь должен иметь возможность искать других пользователей по имени/email.
4) Пользователь должен иметь возможность отправлять заявку в друзья и принимать её.
5) Пользователь должен видеть список своих друзей.
6) Пользователь должен видеть рейтинг среди друзей.
7) Пользователь должен видеть свой ранг и позицию в общем рейтинге.
8) Система должна уведомлять о том, что друг обогнал пользователя в рейтинге (см. модуль 8).

### 7. Подписки и оплаты

1) Система должна поддерживать платную подписку (премиум-тариф).
2) Пользователь должен иметь возможность оформить подписку и оплатить её.
3) Система должна поддерживать оплату через платёжные системы (в т.ч. подписки магазинов приложений).
4) Система должна проверять статус подписки (активна/истекла) при доступе к премиум-функциям.
5) Система должна автоматически продлевать подписку (при наличии автопродления).
6) Система должна уведомлять о скором окончании подписки.
7) Система должна обрабатывать отмену подписки.
8) Система должна хранить историю платежей пользователя.
9) Система не должна хранить и обрабатывать платёжные данные в открытом виде.

### 8. Нотификации

1) Система должна уведомлять пользователя о длительном отсутствии (не занимался N дней).
2) Уведомление о неактивности должно иметь эскалацию: более мягкое при короткой паузе и мотивирующее при длинной.
3) Система должна отправлять ежедневный квиз по настраиваемому времени пользователя.
4) Система должна уведомлять о новом контенте в любимых категориях пользователя.
5) Система должна уведомлять о достижениях и прогрессе (завершён уровень, побит рекорд).
6) Система должна уведомлять о социальных событиях (приглашение, соперник обогнал).
7) Система должна уведомлять о статусе подписки (скоро закончится, истекла, предложение).
8) Уведомления должны доставляться по каналам Push и Email.
9) Пользователь должен иметь возможность настраивать, какие типы уведомлений получать.
10) Пользователь должен иметь возможность настраивать время и тихие часы.
11) Система должна ограничивать число уведомлений в сутки и не отправлять в тихие часы.
12) Система должна предотвращать дублирующиеся уведомления.
13) Пользователь должен иметь возможность просматривать историю уведомлений и отмечать прочитанными.

### 9. Сбор аналитики

1) Система должна принимать события из мобильного приложения.
2) Система должна собирать события навигации и кликов (открытие экрана, кнопки, вкладки).
3) Система должна собирать события по контенту (просмотр, выбор, старт, завершение).
4) Система должна собирать события по квизам (старт, завершение, выбор ответа, подсказка, ошибки).
5) Система должна собирать события по социальному модулю (поиск друга, добавление, соревнование).
6) Система должна собирать события по монетизации (просмотр предложения, покупка) без платёжных данных.
7) Система должна собирать события по нотификациям (получение, открытие, конверсия).
8) Система должна связывать события с пользователем и сессией и хранить временные метки.
9) Система должна хранить события аналитики в ClickHouse.
10) Система должна обеспечивать приём событий без потерь и дедупликацию.
11) Система должна строить дашборды: DAU/WAU/MAU, сессии, длительность.
12) Система должна строить дашборды вовлечённости: просмотры, дочитывания, время на формат.
13) Система должна строить дашборды обучения: квизы, % верных ответов, темп программы.
14) Система должна строить воронки: онбординг → первый квиз → регулярное возвращение.
15) Система должна строить дашборды монетизации: конверсия в премиум.
16) Система должна строить дашборды эффективности нотификаций: CTR, возврат, отписки.

## Нефункциональные требования

1) **Производительность**: отклик API-эндпоинтов не должен превышать 300 мс в среднем (p95 — не более 1 с) при типовой нагрузке.
2) **Масштабируемость**: архитектура должна допускать переход от монолита к микросервисам без переписывания бизнес-логики.
3) **Доступность**: сервис должен обеспечивать доступность не ниже 99.9% в месяц.
4) **Надёжность**: приём событий аналитики не должен терять данные при сбоях; допускается отложенная доставка.
5) **Консистентность**: события должны быть идемпотентными (дедупликация по идентификатору события).
6) **Безопасность**: хранение и передача данных должны быть защищены (шифрование, безопасные пароли, токены).
7) **Защита данных**: персональные данные обрабатываются в соответствии с требованиями к конфиденциальности; событий аналитики без явного согласия не собирается.
8) **Аудит**: действия администрирования (модерация контента, отправка массовых уведомлений) должны логироваться.
9) **Наблюдаемость**: сервис должен иметь логирование, метрики и поддержку трейсинга для диагностики.
10) **Тестируемость**: бизнес-логика должна покрываться автоматическими тестами; обязательны тесты в CI.
11) **Совместимость**: API должно быть обратно совместимым; изменения версионируются.
12) **Интернационализация**: структура данных должна допускать добавление локализаций контента и интерфейса.
13) **Качество контента**: публикуемый контент должен проходить модерацию (корректность фактов, отсутствие нарушений).
14) **Удобство использования**: интерфейсные решения должны следовать принципам понятности и ненавязчивости (особенно нотификации).
15) **Отказоустойчивость**: при недоступности внешних сервисов (push-провайдер, платёжная система) запросы должны корректно обрабатываться и не приводить к потере данных.
